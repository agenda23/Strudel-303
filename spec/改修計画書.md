# 改修計画書: Strudel × TB-303 アシッドテクノ作曲ツール

作成日: 2026-10-09 / 対象: `D:\workspace\303seq` 一式 / 基準文書: `spec/Strudel × TB-303 仕様・開発手順書.md`（以下「仕様書」）

## 1. 結論（要約）

**「Strudelベースのアシッドテクノ作曲ツール」としては、土台は妥当だが、現状は未達である。** 過不足の内訳は次のとおり。

- **妥当な点**: Strudel本体を改造せず `@strudel/web` に依存し、303だけを自作ワークレットで足す方針は正しい。`.s("tb303")` と `accent` / `slide` / `tb*` のコントロール、PolyBLEP VCO、非線形ダイオードラダー、MEG/VEG、アクセント蓄積、サンプル精度のイベントキュー、コード入力UI、909同期再生まで、骨格は動く形で揃っている。
- **不足している点（致命的）**: 303の要である**スライドが既定設定では効かない**。ワークレットの**時間基準がずれて909と同期しない可能性が高い**。303の出力がStrudelのオービットを通らず、**delay / reverb / gain / pan が使えない**。**BPMが既定の120のまま**で、アシッドテクノの帯域（130〜145）に合わない。
- **過剰な点**: 仕様書のスコープ外の機能（AIコンポーザー、MCPサーバー、マニュアルモーダル）が先に作られている。これらにはセキュリティ上の欠陥がある（§3.3）。一方で、本命の「音の追い込み」（フェーズ5）と検証（参照音との比較、回帰テスト）は手付かずである。
- **仕様との乖離**: 仕様書の「DSPコアは純TSを1つだけ持ち、ワークレットはそれを呼ぶ」が守られていない。ワークレットのコードが `src/worklet/processor-code.ts` に手でコピーされ、`src/dsp/` と二重化している。テストはコピー元の `dsp/` しか見ていないので、**実際に鳴るコードは無テスト**である。

仕様書のフェーズ進捗は、フェーズ1〜4は形式上完了、フェーズ0（調査記録）・5（追い込み）・6（公開・拡張）は未完了、と評価する。

## 3. 精査結果（問題点）

優先度: **P0**=作曲ツールとして成立しない / **P1**=アシッドテクノの品質・実用に必須 / **P2**=品質向上 / **P3**=整理。

### 3.1 正しさの問題（P0）

| ID | 問題 | 根拠 | 影響 |
| --- | --- | --- | --- |
| B1 | **スライドが既定で効かない**。`triggerNote` は「ゲートがまだ開いているときだけ」スライドする（`tb303.ts` の `slide && this.gate`）が、ゲート長は既定で `duration × 0.85`（`bridge.ts` の `legato`）なので、次ノート開始時にはゲートが閉じている | `legato(1)` 以上を明示しない限り、`slide` は常に通常の再トリガーになる。`dsp.test.ts` のスライド検証は0.1秒ゲート・2000サンプルで偶然通るだけ | 303の核心機能が使えない |
| B2 | **スライドの意味が仕様と逆**。仕様書は「そのステップから**次**のステップへ」（ルール3: 前のノートが `slide=1`）。実装は「そのステップ**へ**滑り込む」（現在ノートの `slide` を見る） | 例 `slide("0 0 1 0 ...")` が仕様では3拍目→4拍目、実装では2拍目→3拍目になる | 実機のシーケンス感覚・手順書の例と食い違う |
| B3 | **時間基準のずれ**。ワークレットは自前の `frameCounter`（ノード生成時に0から開始）と `time * sampleRate`（AudioContext絶対時間）を比べている。`AudioContext` は `ensureAudioReady` の時点で既に走っており、ノード生成までの経過分だけ303が**遅れる** | 実測で確認する（§5 T1）。グローバルの `currentFrame` を使えば解消する見込み。`audioworklet.d.ts` に宣言はあるが使われていない | 909・ブレイクとの同期という成功定義に反する |
| B4 | **パラメータが固着する**。`Object.assign(voice.params, evt.params)` はイベントに含まれる項目だけ上書きするので、`tbdist` などをコードから消しても前の値が残る。UIスライダーの `setDistortion` とパターンの `tbdist` も衝突する | 評価し直しても音が元に戻らず、再現性がない。`reset` は停止時のみ | ライブ編集で状態が汚れる |
| B5 | **クリック**。ノート開始で VEG を1.0に即時セット（アタックなし）、ゲートは瞬断、MEGも即時1.0。発音時の位相も不連続 | 仕様の検証項目「クリック」に未対応。波形確認テストもない | 高音量・低カットオフで目立つ |

### 3.2 アシッドテクノ作曲ツールとしての不足（P1）

| ID | 不足 | 詳細 |
| --- | --- | --- |
| F1 | **オービット／マスター系統に載っていない** | 303は `AnalyserNode → destination` に直結している。`.delay` `.room` `.gain` `.pan` `.orbit` `.duck` が効かない。アシッドの定番（ディレイ付き303、サイドチェイン）が書けない。仕様書フェーズ6の `registerSound` 方式（第2段階）がこれに当たる |
| F2 | **BPMが既定120** | プリセットが `setcps` / `.cpm` を指定していない。アシッドテクノの帯域（130〜145）にならない。BPM表示・変更UIもない |
| F3 | **テクノ用ドラムの手当てが薄い** | 909は `bank("RolandTR909")` のみ。ハット開閉のチョーク（`cut`）、サイドチェイン、キックの歪み、ライド・クラッシュ・リムのプリセットがない。サンプル取得先がGitHub生URL／`github:` 固定で、オフライン・取得失敗時の挙動が不明（取得も2回重複） |
| F4 | **303の表現力** | 音量（`gain`）・ベロシティが無視される。波形はsaw/squareのみ。オクターブ範囲の検証がない。MEGの上限（`3.5`オクターブ固定）、アクセント量、サブオシレータは調整手段がない |
| F5 | **作曲支援がない** | 再生位置のハイライト、ステップの可視化（`pianoroll` 等）、BPM／キー変更、パターンの保存・読み込み・共有URL、曲全体のオフラインWAV書き出し（`tools/render.ts` は固定16ステップのみ）。コードは保存されず、リロードで消える |
| F6 | **ライブ編集時の挙動** | 評価時に303のキュー・状態を整理しない（B4）。エラーはコンソールとステータス文字だけで、エディタ上の位置表示がない。`tb303` 以外のシンタックスエラーの案内がない |

### 3.3 仕様外の追加物の問題（P1〜P2）

| ID | 問題 |
| --- | --- |
| X1 (P1) | **MCPサーバーのWebSocketが無認証**。`new WebSocketServer({ port })` はホスト指定なし（全インターフェースで待受）、Origin検証なし。ブラウザ側は受け取った `code` をそのまま `evaluate` する。起動中は、同一ネットワークまたは任意のWebページから任意のJSをこのアプリのオリジンで実行させられる |
| X2 (P2) | Gemini APIキーを `localStorage` に平文保存し、`?key=` のURLクエリで送信、設定UIは `prompt()` / `alert()`。AI機能は仕様書に無い |
| X3 (P2) | プリセット・プロンプト・MCPの `get_reference` が似た内容を3か所で別々に持つ（`main.ts` / `composer.ts` / `mcp/server.ts`）。パラメータ追加のたびに食い違う |
| X4 (P3) | `main.ts`（600行）に UI・Strudel初期化・MCP・オシロが同居。`evalScope` を二重に呼ぶ、`Pattern.prototype.tb303`（未使用）を生やす、など整理不足 |

### 3.4 DSPの忠実度（P2。仕様書フェーズ5が未実施）

- **ラダーの帰還は1サンプル遅延**で、ZDF（同時解法）にしていない。入力はゼロ次ホールドで2倍オーバーサンプリングしており、ダウンサンプル側のフィルタもない。高カットオフ・高レゾナンスでエイリアスが残りうる。`tan()` を毎サンプル計算している。
- 実機は約18dB/oct的な応答で、レゾナンス時にローが痩せる。今の4ポール・均一段・`k` 最大3.8は「ムーグ型」に近く、ダイオードラダー固有の段間結合は入っていない。
- アクセントは「ON時の係数」が経験則（`0.7` / `0.5` / `1.4` / `0.35s` など）で、参照音に基づく根拠の記録がない。VEGにディケイ・アタック整形がない。スライドは指数カーブ・60ms固定で未検証。
- 既存の `ftype("ladder")`（superdoughにラダーあり）と聴き比べた記録がなく、「自作が必要か」の判断（仕様書フェーズ0）が文書化されていない。
- ライセンス: `@strudel/web` は AGPL-3.0-or-later。リポジトリにLICENSE・`package.json` の `license` がなく、公開時のソース公開の整理が未了。

### 3.5 品質保証の不足

- 実行コード（`processor-code.ts`）に対するテストがゼロ。`dsp/` と文字列コピーの差異を検出できない。
- 仕様書「検証・品質基準」のうち、音色再現・エイリアシング・タイミング（10分連続）・クリック・WAV回帰が未実装。CPU試験は実時間計測でCIでは不安定になりうる。
- `scratch/*.wav` は出力物で、基準データとして管理されていない。

## 4. 改修方針

1. **DSPコアを1か所に集約**（ワークレットは `dsp/` を直接import）。実際に鳴るコードをテスト対象にする。
2. **仕様どおりの意味論に直す**（スライド＝前ノートの `slide` が次ノートへの遷移を決める）。
3. **303をsuperdoughのサウンドとして登録**し、オービットに載せる。
4. 作曲体験（BPM、可視化、保存、書き出し）を、仕様外機能より先に厚くする。
5. 仕様外機能は、安全性を直した上で切り出す（または既定オフ）。

## 7. リスクと未確認事項

- B3は静的な読みに基づく推定である。T1の実測で確認してから修正する（原因が別なら B-1 を差し替える）。
- `registerSound` の仕様（Strudel 1.3.0 の superdough）は、フェーズAのT3でソースを読んで確認する。ワークレットの単音常駐とノード単位の接続が両立しない場合は、現行の `defaultOutput` 差し替えを維持しつつ、出力側だけをオービットへつなぐ代替案を検討する。
- 「303らしさ」の合格判定は聴き比べで、数値だけでは決まらない。参照音の入手方法（自己録音）を先に決める必要がある。
- Strudelのバージョンアップで内部APIが変わる可能性がある。`package.json` のバージョン固定とスモークテストで備える。
